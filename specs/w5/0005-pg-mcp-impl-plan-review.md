# PostgreSQL MCP Server 实现计划 Review

## 总体评价
计划分阶段清晰，关键路径明确，任务粒度可执行。但相对 PRD/设计文档仍缺少若干安全与运维细节，需在计划中补充，否则落地时存在安全与可用性风险。

## 主要问题与风险
- **参数化与常量约束缺失（高优先）**：计划未明确“所有执行 SQL 必须使用参数绑定，不允许 LLM 直接插值常量”。PRD F-026 要求防注入，当前任务列表未覆盖参数化执行与文字常量校验。
- **健康检查与指标缺失（高优先）**：NF-013/监控未落到任务。Phase 5 仅提日志/熔断，缺少健康探针、核心指标（DB/LLM延迟、限流/熔断状态、缓存命中率、查询耗时、LLM错误率、截断率）。
- **Schema 自动刷新落地不足（中优先）**：设计中提示支持 TTL + 后台刷新，但计划未安排定时调度任务、刷新状态暴露、失败回退/限流。F-009/F-010 需有明确实现与验收。
- **成本/Token 计量与告警缺失（中优先）**：NF-018 需要 token/费用监控与阈值告警，计划未覆盖。
- **日志脱敏与最小化（中优先）**：虽采用 structlog，但未安排“禁止记录敏感列/样本、LLM请求脱敏”任务，存在泄漏风险（NF-008）。
- **分页与硬上限测试未量化（低优先）**：硬上限/分页截断逻辑（默认200/硬1000）在验收标准中未有明确测试项。

## 建议的计划补充/调整
1. **参数化执行**  
   - 在 Phase 3 QueryService 增加任务：执行层统一使用 asyncpg 参数绑定；LLM 生成的 SQL 禁止内插常量/字符串拼接；必要时对文字常量做白名单或长度限制。  
   - 验收标准新增：无用户输入直插 SQL；恶意常量用例（引号闭合、分号、注释）被拦截或参数化。

2. **健康检查与指标**  
   - 在 Phase 5 增加任务：实现健康探针（LLM可选降级，DB/LLM/缓存状态）；输出核心指标（查询耗时P50/P95、LLM成功率、限流/熔断计数、缓存命中率、截断比例）。  
   - 验收标准：健康检查可被外部探测；指标可被导出或打印（最简：stdout/structlog，可扩展 Prometheus）。

3. **Schema 自动刷新落地**  
   - 在 Phase 3 SchemaService 增加：定时任务调度（auto_refresh_interval_hours>0 时起循环任务）、刷新状态暴露、失败回退保留旧缓存、单库串行/并发限流。  
   - 验收标准：可通过接口/日志看到刷新状态；失败不影响已有缓存。

4. **成本/Token 计量**  
   - 在 Phase 5 增加：LLM 调用 token/费用计量，阈值告警或降级策略（例如仅返回 SQL / 跳过验证）。  
   - 验收标准：达到阈值时可观测并触发降级。

5. **日志脱敏与最小化**  
   - 在 Phase 5 增加：日志中禁止记录敏感列/样本，LLM 请求/响应脱敏后再记录；SQL 执行错误时仅打印摘要。  
   - 验收标准：敏感列名、行样本不出现在日志。

6. **分页/硬上限测试**  
   - 在 Phase 6 测试项中加入：max_rows/hard_max_rows/pagination 行为校验，截断标记、行数符合预期。

## 结论
计划整体方向正确，但需补齐安全、监控、成本与自动刷新的实施与验收项，以满足 PRD/NF 要求并降低上线风险。请在 0004 计划中加入上述补充任务和验收标准。
